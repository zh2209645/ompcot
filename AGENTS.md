# Ompcot

## Product

**Ompcot** is a local desktop GUI for the OMP coding agent. It is a Tauri app that spawns one `omp --mode rpc` subprocess per workspace, each on its own port, running the **system `omp` from the user's PATH** (overridable via the `OMP_BIN` env var) — there is no bundled omp binary anymore (`scripts/fetch-omp-binary.js` is a kept-as-no-op; `scripts/omp-version.json` is gone). Each workspace gets its own OS window.

```
Ompcot .app
  resources/
    public/                        (frontend, vanilla JS — no framework)
    extensions/dist/embedded-server.mjs (HTTP + WS server, runs inside omp as an extension)
  Rust OmpManager
    spawn omp --mode rpc --extension embedded-server.mjs  (project A, :3001)
    spawn omp --mode rpc --extension embedded-server.mjs  (project B, :3002)
    OS Window per project  →  WebView  →  localhost:300X
  omp resolved from PATH (or OMP_BIN)
```

Tauri IPC commands (invoked via `window.tauriNative` in `public/tauri-bridge.js`):
- `cmd_open_workspace(cwd)` — spawn omp for a workspace, open a window
- `cmd_new_session(port)` — create a new session in a running omp
- `cmd_switch_session(port, sessionPath)` — resume a historical session
- `cmd_stop_instance(port)` — kill a omp process
- `cmd_pick_folder()` — native folder picker

### Goals

- Local desktop GUI: all projects and agents visible in one app
- Multi-project: each project has its own window, isolated working directory, session history, and running agent
- Multi-agent: one `omp --mode rpc` process drives **one active session** at a time, so every concurrently-running session gets its own omp process. "+ New Session" and sidebar "start new chat" spawn a fresh **headless** omp and navigate the current WebView to it — no new OS window, previously-running sessions keep running.
- Bilingual UI (English / 简体中文) with a Settings picker; preference persisted in a cookie so all workspace windows (different localhost ports) share it
- Visualization: streaming chat, tool-call cards, thinking blocks, token/cost tracking per session
- Self-contained desktop app; the only external requirement is `omp` on PATH

### Feature surface (as of v0.8.3)

- Chat: streaming, tool cards, thinking blocks, abort, queued messages with Queue/Steer-now delivery, queued slash commands (composer `/` autocomplete backed by `list_commands`; slash prompts execute when omp is idle, auto-queue while streaming), file mentions (composer `@` autocomplete over `/api/files`, an "attach file or image" multi-select on the native host, and drag-from-the-file-pane — all inserting omp's own `@path` grammar, which the runtime auto-reads; images take the same route, there is no separate image-attach path: base64 `prompt.images` and the composer previews were removed rather than kept broken)
- Compaction: manual `/compact` (omp's own builtin — `/compact soft|remote|snapcompact [focus]` — reachable from the composer because slash prompts go through the runtime's dispatch) plus the GUI's own entry points, the header's **Compact** button (rendered at ≥80% context) and the command palette's Compact action, which send the same `{type:"compact"}` command. The extension drives `ctx.compact`, reports `auto_compaction_start/end`, re-broadcasts the session snapshot once the summary is committed so the transcript gains its compaction item and the pill shows the *post*-compaction size, and reports a no-op or a summarizer failure as an inline "Compaction failed — …" line with the context left exactly as it was
- Model & reasoning: model dropdown, per-model thinking-depth menu (levels resolved from `ctx.model.thinking.efforts`; non-controllable models disable the controls), Configuration → Models & Reasoning page (default model + default thinking depth, 15 model roles, task-agent model overrides/disable — selectors composed as `provider/model:effort`)
- Sessions: history/search/favourites/archive/rename/batch-delete, export HTML, fork from any message (works on omp ≥18.3.1: broker native RPC `branch` + `session_branch` event ack; WS `ctx.branch` path kept for future builds), rewind to a user message (`/ompcot-rewind <entryId>` — an extension command whose handler owns omp's `navigateTree`; the message text returns to the composer and the handler re-broadcasts the snapshot), transcript re-sync, external import entry points (honest interactive-only guidance)
- Agent Hub: right-dock panel with live agent roster (`AgentRegistry`), status, and read-only nested transcript viewing
- MCP management: Configuration → MCP page — server cards, add/edit (stdio/http/sse) via omp's own validators/writers (file-URL import of the `/mcp` module), enable/disable with persistence; live connection status honestly degraded when the bundled omp build can't expose it
- Interactive UI requests: omp's `extension_ui_request` loop (select/confirm/input) fully interactive — replayable pending dialogs, absolute deadlines, cancel frames
- Settings: General (Appearance themes + language), Extensions (package browse with configurable registry + offline cache), Usage (account usage via `omp usage --json` + local cost dashboard), Configuration sub-pages (Providers incl. API keys + OAuth login via `omp login` subprocess / Appearance / Model / Interaction / Context / Memory / Files / Shell / Tools / Tasks / **Models & Reasoning** / **MCP** / **Other** / Advanced)
- Themes: 6 built-in + 9 VS Code schemes + Windows Terminal theme import (windowsterminalthemes.dev JSON, cookie-persisted, cap 20)

### Constraints

- Frontend: vanilla JS, no framework (`public/`)
- Backend: Rust (Tauri) manages process lifecycle; the Node/TS extension (`extensions/embedded-server.ts`, bundled to `extensions/dist/embedded-server.mjs`) implements the HTTP + WS surface
- omp integration: always via the spawned `omp --mode rpc` subprocess — never re-implement runtime logic. When omp lacks an extension API, prefer in-process surfaces (`currentOMP()`, settings, registry) then CLI fallbacks (`omp config`, `omp usage`, `omp login`); degrade honestly in the UI rather than faking state
- The running omp version is whatever the user has installed; the GUI feature-detects surfaces per build
- User extensions under `~/.omp/agent/extensions/` and `<workspace>/.omp/extensions/` are auto-loaded by omp itself

### omp references

Local install (authoritative for the running version): `~/.bun/install/global/node_modules/@oh-my-pi/pi-coding-agent/dist/types/` (readable `.d.ts`; `dist/cli.js` greppable). Upstream: `can1357/oh-my-pi` on GitHub.

# Agent working notes

Conventions for any coding agent working in this directory.

## Package manager

Use **Bun** exclusively. Never run `npm install` or `npm ci` — this would create a stray `package-lock.json` that drifts from `bun.lock`.

```bash
bun install --frozen-lockfile   # install deps
bun run <script>                # run package.json scripts
```

## Common commands

```bash
bun run dev              # start tauri dev (hot reload)
bun run test             # vitest run + check-tauri-permissions
bun run test:watch       # vitest in watch mode
bun run check:rust       # cargo check + clippy + fmt (use after every Rust edit)
bun run build:extensions # compile extensions/embedded-server.ts → extensions/dist/embedded-server.mjs
bun run build            # full release build (prebuild: build:extensions)
```

Single test file: `bun run vitest run public/settings-save-status.test.js`

## Linting & Formatting

Biome for JS/TS. After every frontend or extension edit:

```bash
bun run check         # read-only
bun run check:fix     # auto-fix safe issues
```

- **Always** run `bun run check` (or `bunx biome check <touched files>`) after editing `.js`/`.ts` under `public/` or `extensions/`; only mark work done if it exits 0 for your files. Note: the repo-wide check has **pre-existing CRLF-drift failures in untouched files** on Windows checkouts — scope your checks to the files you touched.
- Windows checkouts flip files to CRLF; agents must re-normalize their touched files to LF before committing (biome `--write` on the touched set).

## Module Design

The frontend is vanilla JS with **no framework**:

- **One concern per file**; kebab-case filenames matching the responsibility
- **Avoid growing `app.js`** — it is the entry orchestrator; new feature logic belongs in a dedicated module imported from app.js
- **New file threshold**: >~50 lines of logic → own module
- **No shared-state side-effects at import time**
- **i18n is mandatory** for user-facing strings: `t(key, params)` from `public/i18n.js` for JS-rendered text, `data-i18n*` attributes for static markup; keys live in `public/locales/en.js` + `zh-CN.js` (flat dotted, 1:1 parity enforced by `public/i18n.test.js`); JS-built chrome re-renders via `onLanguageChanged`. Cookie-persisted preferences (`ompcot-theme`, `ompcot-lang`, …) — NOT localStorage — because workspace windows live on different localhost ports (origins); cookies are shared across ports.
- **RPC pattern**: one-shot calls go through `public/ws-rpc.js` (`wsRpc(wsClient, {type, ...})` → `{ok, data}|{ok:false, error}`); request ids are per-window prefixed (collision-proof across windows)

## Architecture

**1. Rust / Tauri (`src-tauri/`)** — process lifecycle and window management.
- `src-tauri/src/omp_manager.rs` — spawns `omp --mode rpc --extension <bundled embedded-server.mjs>` per workspace, port allocation, RPC forwarding (broker WS between WebViews and each omp).
- `src-tauri/src/main.rs` — Tauri commands (`cmd_open_workspace`, `cmd_new_session`, `cmd_switch_session`, `cmd_stop_instance`, `cmd_pick_folder`).

**2. Frontend (`public/`)** — vanilla JS modules: `app.js` (orchestrator), `websocket-client.js`/`transport.js`/`ws-rpc.js` (WS + broker RPC), `message-renderer.js`/`tool-card.js`/`markdown.js`/`scroll-follow.js`/`transcript-view.js`/`composer-input.js`/`composer-mentions.js`, `session-sidebar.js`, `file-browser.js`, `agent-hub.js`, `mcp-manager.js`, `models-reasoning.js`, `composer-commands.js`, `thinking-level-menu.js`, `ui-requests.js`, `account-usage.js`, `agent-settings*.js`, `themes.js` + `theme-import.js`, `i18n.js` + `locales/`, `dialogs.js`, etc.
- Transcript layout: assistant messages are width-locked to the **full text column** (`width: 100%; max-width: 100%` on `.message.assistant`) so the blocks inside them — thinking blocks, code, tables — render at one uniform width *and* share the left/right edge of the tool cards and the composer card. They used to shrink to their content, which made the same block render as a label-width pill in a thinking-only turn and a full-column bar under a paragraph; the 85% cap that replaced it (`max-width` on `.message`, still what the right-aligned user bubble uses) left reply text and thinking ~144px short of the tool cards and the input box, which read as the input box being misaligned with the conversation
- Typography: every text size in the stylesheets is written as `calc(<px> * var(--font-scale))`, families come from `var(--font-ui)` / `var(--font-mono)`, and Settings → General → Fonts (`public/font-settings.js`, `ompcot-font` cookie, shared across workspace windows) overrides those variables on `<html>`. A literal `font-size: 13px` would silently opt that element out of the user's font size
- Transcript identity: every transcript item is rendered by identity, never appended blind — assistant messages are keyed by `data-message-id` (a replayed/retried frame re-adopts its element, a streaming render adopts the newest *unfinished* element so distinct turns never merge), tool cards are keyed by `toolCallId` and re-targeted when a re-render detached them, and `message_end` only finalizes the assistant element it belongs to. The id is resolved inside the extension by role + timestamp (`matchMessageEntryId`, `extensions/embedded-server.ts`) and **retried for a few ms**: omp persists a message *after* its `message_end` handler runs (measured 11–20 ms on 18.3.2), so a synchronous lookup found nothing and every live element kept the `"streaming"` placeholder — fork-from-message on a fresh reply and element re-adoption then fell back to content matching. Only frames no later frame of the same message can overtake wait (any `message_end`, a user message's `message_start`); streaming frames stay immediate. That wait is also what puts the identified assistant `message_end` *behind* `agent_end`, so the run end finishes the live element while it still carries the `"streaming"` placeholder — every assistant element therefore carries its runtime identity too (`data-message-ts`, the same role+timestamp key the extension resolves entry ids with) and `handleMessageEnd` adopts a settled element by it (`findSettledAssistantElement`) when neither the entry id nor the unfinished flag matches; without that rule the late identified frame appended a second copy of the reply, which the debug bundle's own duplicate detector caught as `same-content` with one `null` id. The *streaming* path needs the same identity rule, and lacked it: the runtime flushes a turn's final partial on its way out (`agent_end`, then a `message_update` for the same message 7ms later in the reported bundle — streaming frames stay immediate by design, only the identified `message_end` waits), so a `message_update` — or a replayed `message_start` — can arrive for a message the run end already finalized. `findSettledAssistantElement` deliberately matches only elements still on the `"streaming"` placeholder (its job is the *unidentified* settle), so an element that had already received its real entry id from an earlier identified update was missed by every adoption step and `renderAssistantMessage` appended a second copy: the bundle's pair of elements at `ts 1790562840193`, one `4d13d778` and one `"streaming"`. `handleMessageUpdate`/`handleMessageStart` now ask `findFinalizedAssistantElement(entryId, ts)` first and drop the frame (`debugLog` `stream.late-update` / `stream.late-start`, `action: "dropped"`), and `renderAssistantMessage` never walks a known entry id back to the `"streaming"` placeholder. The census's duplicate detector groups by `data-message-ts` too (`same-message-ts`), because both older keys miss exactly this pair: the id check skips `"streaming"`, and the finalized copy's rendered markdown differs from the live copy's raw text within the compared prefix. The finders are answered from an **identity index** the renderer maintains (`assistantsById` / `assistantsByTs` + an ordered `assistantOrder`), reset by `clear()` and refreshed when a late entry id lands on a finalized element: they used to walk `container.querySelectorAll(".message.assistant")` per lookup, i.e. once per rendered entry and once per streamed frame, and the census line (`transcriptState`) added a `querySelectorAll` plus a full-text pass over every assistant element on top — measured **5470 scans / 1.06 s** while hydrating that session, 7.4 ms per streamed frame for the text pass alone, paid with capture on (the default). The census is now O(1) (counts come from the index; the content-prefix duplicate key, the one check that must read text, is throttled to once every 2 s on the automatic path and immediate for an explicit call), which took the same hydration to **80 scans / 50 ms** and 11.5 s → 2.7 s end to end. Without the identity, any repeated frame (provider retry, snapshot-vs-live overlap, transcript re-render mid-turn) showed the same reply, thinking block or tool card twice
- Transcript rendering: the live stream renders from the runtime's cumulative partial message (thinking segments one block each, no delta accumulation), and `finalizeStreamingMessage` rebuilds through the *same* content-block builder the history/reload path uses (`assistantContentHtml`), so a message looks identical whether it was streamed or re-read from the session file. The live thinking accumulator belongs to the message that produced it — it is cleared at run end, and `updateStreamingThinking` drops blocks past the reported segments — because an element adopted across messages (a dropped `message_start`) otherwise kept the previous reasoning chain on screen next to the new one. Repeated UI passes guard their writes — header status text/dot (`setStatusText`/`setStatusIndicatorState`) and the Agent Hub roster (structure/status signatures + in-place status labels) only touch the DOM when a value actually changed, so polling never flickers labels or restarts their animations
- Transcript scrolling: one follow policy (`public/scroll-follow.js`) for `#messages`, shared by the message and tool-card renderers, plus one instant-jump primitive (`jumpToBottom`). The layout is plain flow — `.main` is a flex column of header, transcript, composer, so nothing overlays the transcript and no message can be drawn under the input box (`layout-insets.js`, `--messages-top/bottom-inset` and the `scroll-padding-*` they fed are gone; `.messages-wrap` exists only to anchor the scroll-to-bottom button over the transcript). The composer still changes the transcript's *box* without any scroll (a queued-message chip, the streaming toolbar, a wrapped draft each take height from the column), and the browser keeps `scrollTop` through that, so a reader who was at the bottom ended up 50–150px short of the content end with the newest message below the fold: a `ResizeObserver` on `#messages` re-pins them (`ScrollFollow`), while a reader parked mid-history keeps `scrollTop` byte-identical. That protection now covers the settle window too: `anchorHistoryToBottom`'s two delayed passes (80/160 ms, for late markdown/image layout) skip once the reader is more than a viewport away from the end, because with tail-first hydration a scroll-up through history happens inside that window and being yanked back to the bottom is exactly what it looks like. `ScrollFollow.isPinned` is **state, never a measurement**: the renderers ask it on every rendered entry and every streamed delta, and a geometry read there forces a synchronous layout of the whole transcript — measured **28 ms** on an 80k-node / 3775-item session, paid per update. Only a real scroll (`noteScroll`, from the scroll event) or `reset()` changes it, and `reset()` is what the renderers call when they throw the transcript away (`MessageRenderer.clear` / `ToolCardRenderer.clear`), which is where the old getter's "nothing to scroll is pinned" self-heal now lives. Both renderers also coalesce their follow to **one jump per frame** (`followFrame`), because a running command or a stream delivers many updates per frame and every jump clamps against the content end — the read that forces the same layout. `pinned` is state, not a per-call measurement — content growth never unpins, only a real scroll does, and a container with nothing to scroll re-pins itself (a re-render that replaces a long transcript with a short one leaves no scroll position — and no event — to correct a stale flag). The *local* user's own message is the one deliberate exception: `renderUserMessage(…, { forceScroll })` jumps for it even when the feed is unpinned (and jumps *immediately*, then again on the next frame) — the follow policy protects a reader's place from *incoming* content, but the capsule they just sent was appended below the viewport and sat out of sight until they scrolled by hand. The send path and the queued-delivery path pass it; a message echoed from another surface (mirror mode, a TUI client) does not. `@keyframes msgIn` is opacity-only for the same reason: with `translateY(8px) scale(0.98)` a freshly sent capsule drew 8px low (measured bottom 671 vs composer top 629, the scroller clipping 61px) and its scaled 24px radius over a `backdrop-filter: blur` layer read as an irregular outline before it settled.
- Transcript ownership: `public/transcript-view.js` arbitrates who owns the surface. The Agent Hub's "view transcript" is a peek that renders a session file into `#messages` without changing routing, while the foreground session keeps streaming — so live transcript events (`transcriptView.suppresses` over the transcript-event set in `public/transcript-view.js`) and `mirror_sync` repaints are dropped while a peek is active, and every claim carries a token so a history fetch or peek response that resolves late (two quick clicks, a selection landing mid-load) cannot paint over the view the user navigated to. A peek is *all* a subagent row can do (`public/transcript-open.js`): routing that button through the sidebar's selection flow cleared the composer queue, reset the transcript state (dropping the sidebar's running mark) and — for a session that was streaming — could spawn a second omp process for the run already in flight, re-routing the window to it, which read as "view transcript switched me to another session". The `main` row is the exception and carries its kind through the click (`agent-hub.js` passes `"main"`/`"sub"`): it is this process's own session, so it always means "hand the surface back to the live view" (claim + `mirror_sync_request`) and is never compared against the live files or peeked. That comparison cannot be trusted anyway — omp registers the main agent once, at process start, and its registry ref keeps that registration's session file, so after a `new_session`/switch/fork the roster named a session the process had already left; the extension therefore rewrites the main row's `sessionFile` from the published ctx (`applyLiveMainSession`, `embedded-server.ts`), the same source the instance registry uses. The remaining path comparison normalizes spelling (separators, `\\?\` prefix, Windows case, trailing separator), because producers hand over the same file in more than one form and a literal comparison peeked the window's own session; `agent_start`/`agent_end` are deliberately *not* among the suppressed events, since they paint nothing and carry the streaming state the sidebar dot is derived from. Without the ownership rules the parent's own cards (a running `wait`) appeared inside every subagent transcript, and a snapshot repainted the root session over the peek
- Streaming caret: the transcript caret means "the model is writing you something right now", nothing else. It lives on `.streaming-text.typing` (style.css) and the flag is decided per frame by `isTypingUserText` (`public/state.js`): only a `text_delta` — or, for frames without a delta kind (snapshots, replays), a frame whose user-visible text actually grew — sets it; a thinking or tool frame clears it. Before that, a thinking-only stretch rendered an *empty* `.streaming-text` whose `:empty::after` drew the caret under the thinking block, so the caret showed during reasoning and not during tool calls and meant nothing in particular. "The run is still active" is no longer the caret's job: the header's status dot carries it (`.status-indicator.streaming`, a slow breathe), which is also why the reduced-motion block leaves that one animation running. The caret is now an *invariant*, not just a per-frame decision: a settled element can never carry it (`setStreamingTyping` refuses to arm a caret whose `.message-content` lost `streaming`, and `stopStreaming` strips `typing` from the text div as well as the streaming classes), `settleAllStreaming` isolates each element's finalize so one failure cannot leave the rest of the transcript streaming, and an assistant frame that arrives while no run is active is a replay of a finished turn: the message already on screen is dropped (`stream.late-update`/`stream.late-start`, `action: "dropped-settled"`), one that is not is rendered *settled* (`ensureStreamingAssistantElement(message, false)`). Opening a live element there was the bug behind a caret blinking mid-transcript minutes after the run ended — the window's export showed 76 live elements of which 64 kept `message-content streaming` with no `finalized` flag, each one a frame that reopened (or first drew) a message whose `message_end` had already been handled, so nothing would ever finalize it
- Message actions (`public/ui-requests.js`): assistant messages carry "fork from here"; user messages carry "rewind to here" (desktop only — it needs the broker) and "fork from here" too, so both tree operations are reachable from the message they act on. The buttons are hover-revealed (keyboard focus keeps them visible) and need a real session-entry id: user messages therefore get their id stamped by the renderer (`renderUserMessage`) along with the raw text (`_messageText`) the rewind restores into the composer, since the rendered DOM has lost the markdown markup
- Composer mentions: file context reaches the agent the way omp itself defines it — an `@path` token in the prompt that the runtime auto-reads (`utils/file-mentions.ts`: text truncated at 5 MB, images resized and attached as image content, videos as a contact sheet, directories listed to 500 entries) and persists as a `fileMention` message. The GUI never inlines file content: `public/composer-mentions.js` mirrors the runtime's grammar (`@(?:"([^"]+)"|'([^']+)'|([^\s@]+))`, `@` at a boundary), lists the directory the caret's token walks through `/api/files`, and inserts the real path — workspace-relative while it is inside the session cwd, absolute outside, quoted when it carries whitespace, always `/` separators. That one insertion helper serves the popup, the file pane's drag-into-composer and the native picker, so all three write identical text. The picker (`pick_files` broker control → `transport.pickFiles()`) is gated on `transport.capabilities.native` because only the OS dialog returns real paths; browser/mobile clients keep the popup and the drag path. The button follows the composer it writes into: `refreshAttachFileButton()` is re-run from `updateUI()` and `updateMirrorInputState()`, so it is disabled (dimmed, `pointer-events: none`) whenever the textarea is — a history session is on screen (`.input-area.mirror-readonly` is itself `pointer-events: none`, so a click there reached nothing at all) or a deferred switch is waiting for the run to finish — because a picker that opens against a disabled composer inserts text the user can never send, which reads as "the attach button does not work while the agent is running". A picker failure now reports itself (`composer.attachFailed` in the status line) instead of being swallowed into the console, so "nothing happened" always has a reason on screen
- Composer: `#message-input` sizing and caret visibility live in `public/composer-input.js` (`syncComposerHeight` / `setComposerText`). Every re-measure starts from `height: auto`, which clamps the internal scroll, so a *programmatic* write (restored undeliverable draft, voice transcript, slash command, inserted file path) left a long draft showing its first lines with the caret below the fold; writes now reveal the end whenever the caret is there, and a caret placed mid-draft keeps the browser's own scroll position
- Command execution & rewind (`prompt_upstream` broker control → omp's own RPC `prompt` frame): slash commands must NOT be sent through the extension API. `sendUserMessage` — the path every other prompt takes — passes `expandPromptTemplates: false`, so a `/cmd` reached the model as literal text; omp's RPC prompt path is the one that dispatches extension commands, custom (TypeScript) commands, skills and builtins. The desktop broker therefore writes a real `{type:"prompt", id, message}` frame to the process's stdin and the reply arrives as the usual forwarded frames (`response` for acceptance, `prompt_result` for the terminal status — both are consumed: the second used to log "Unknown message type" on every native prompt). Rewind rides this channel because omp exposes its session-tree primitive (`navigateTree`, the esc-esc rewind) *only* to extension command handlers and hooks: neither the event context the embedded server runs in nor the RPC protocol (which has only the read-only `get_tree`) carries it, so `extensions/embedded-server.ts` registers `ompcot-rewind`, whose handler navigates, broadcasts `rewind_done` and re-broadcasts the mirror snapshot so the UI replays the shortened branch. Browser/mobile clients have no broker: the rewind action is not attached there, while fork still works through the extension WS path
- Context popover (`public/app-context-viz.js`, the header's `NN%` pill): the pill toggles on **`pointerdown`**, not on `click`, because the header is an app drag region — a press that drifts a pixel (or a WebView2 drag that eats the mouseup) produces no `click` on the pill at all, and a press released outside it dispatches `click` on the nearest common ancestor, so the popover opened only for steady clicks and looked dead otherwise. The outside-dismiss listens for `pointerdown` too (so the two can't race one event) and uses `contains()` on both the pill and the panel instead of an exact `target ===` comparison. Opening with no usage data — a fresh session, or a re-render that reset the totals — draws an explicit "no usage yet" line rather than a blank box, since an empty popover is indistinguishable from one that never opened; `updateTokenUsage()` hides the pill when there is no usage and every reset of `lastInputTokens` drops `lastUsage` with it, so the numbers on screen always belong to the session on screen
- Debug capture: rendering bugs leave no trace in the session file (one entry, two elements), so the window records its own evidence — `public/debug-log.js` (console output, window errors, every WebSocket frame in both directions via `wsClient.debugSink`, session-routing decisions from `logSessionRoute`, and transcript operations with the live element ids and message timestamps) and `extensions/debug-buffer.ts` (what the process broadcast, which commands windows sent, which routes they hit). Both are bounded ring buffers that summarize payloads (ids, sizes, routing metadata — never message text or tool output) and fold a streaming run's near-identical frames into one counted entry. Settings → Configuration → Debug shows the live counts, pauses capture and exports one bundle through `POST /api/debug-dump` (the process writes it under `<tmp>/ompcot-debug/` and answers with the path); `GET /api/debug-log` serves the process half, and `window.ompcotDebug` exposes the same snapshot/export from devtools
- Compacting (`handleCompactionStart`/`handleCompactionEnd`, `MessageRenderer.renderCompaction`): a manual compaction's frames have to ride the `{type:"event", event:{type:"auto_compaction_*"}}` envelope — that is the shape the WS client routes to the app's event switch, and the extension broadcast them bare, so they fell into its `Unknown message type` warning and the GUI showed *nothing* for a compaction that had in fact committed (the session file had the entry; the screen had nothing). A committed compaction is a transcript item: the shared entry walk (`renderTranscriptFromEntries`) draws the `compaction` entry as a notice block labelled "Context compacted" with the summary — id-keyed and 320px-clamped like every notice — which is the only remaining record of the summarized stretch, for a live repaint and for a compacted session re-opened later. The end frame never claims success for a no-op: `error` renders "Compaction failed — …" in the transient indicator, leaves the transcript and the pill untouched and restores the ≥80% button the click hid, while success takes the pill from the frame's live `contextUsage` — the snapshot repaint that precedes it derived its number from the kept tail's last assistant usage, which is still the pre-compaction size — and drops `lastUsage`, the popover's per-request breakdown, because that request ran against the pre-compaction context. A compaction is a *long* operation with no other frame in between (a local `soft` pass over a 40k-token session ran 60 s+), so "it is still working" is state, not a guess: the header carries the label and the breathing dot (`authoritativeStatusText`/`updateUI` take compaction before a run — a pass pauses the run) and the transcript line ticks its elapsed seconds (`public/compaction-pending.js`, `ctx.compactingFor`). The outcome replaces that line in place — `✓ Context compacted · 48.1k → 6.2k`, `Compaction failed — …`, `Compaction skipped — nothing to compact`, `Compaction cancelled` — and the outcome branches must never print a success over a pass that changed nothing (`skipped`/`aborted` keep the pill's numbers, since the context is exactly what it was). Two frame shapes land there: this server's GUI frames carry `error`, the host's `auto_compaction_end` carries `errorMessage`/`skipped`/`aborted`. Those frames are deliberately **not** in `transcript-view.js`'s suppressed set: they carry global state (the header, which a peek must not hide) while only the line they draw belongs to the surface, so the handlers test `transcriptView.active` before touching `#messages`. Which frames exist at all was measured on 18.4.0: `auto_compaction_start`/`end` are emitted only by `runAutoCompaction` (reasons `threshold`/`overflow`/`idle`/`incomplete`) and by the shake path — a manual pass (`ctx.compact` from the GUI command *and* omp's own `/compact` builtin through the RPC prompt frame) emits neither, while `session.compacting` (inside the summarize step, the long part) and `session_compact` (the commit) fire for every path. `nextCompactionLifecycle` folds all four into one start/end per pass: `summarize` starts one only when nothing published a start (the auto path's start is already out, and a method fallback summarizes again inside one call), `commit` repaints for every path (the summarized stretch collapses into the item; a transcript left as-is no longer matches the branch) and ends the pass for the paths nobody else reports — the builtin, and a commit with no start seen at all (an extension reload mid-pass). The commit's repaint goes out *before* the terminal frame so the frame's live usage is the UI's last word, and the GUI command's own report skips its fallback repaint when the commit was already seen (`committed`). A shake rewrites the branch's entries without committing an entry, so its end frame carries the repaint instead. omp's `command_output` line ("Compaction complete. Tokens: 148880 -> 41441 (saved 107439).") never reaches a window — it is an RPC frame on the process's stdout, which the Rust broker drops — so the GUI's numbers come from `contextUsage`, not from that text. The builtin's *no-op* is the one path with no frame at all (the command handler catches it and returns silently, throwing before the summarize step), and it is desktop-only work: the composer's `/compact` send arms a short pending window (`isCompactionCommand` → `pendingCompaction.arm()`) that a real start settles and that otherwise ends as "Compaction skipped", because "nothing happened" must read as nothing rather than as silence. The v0.8.18 freeze that this all replaced: `ctx.compact`'s rejection was unhandled, omp treats an unhandled rejection as fatal, and the process exited on the first no-op — an A/B run of that extension against the fixed one shows `[Unhandled Rejection] ManualCompactionNoOpError … PROCESS EXIT {"code":1}` versus a surviving process and a `{"error":"Nothing to compact (session too small)"}` end frame. A dead workspace *looks* like a frozen page: the transcript stops updating, prompts sit in the queue, and a session switch is never confirmed ("运行中的 OMP 未确认会话切换"), which is exactly the reported symptom set — so a "frozen after compacting" report should check the process first (`/api/health`, the instance list). A pass **holds the screen**: `handleMirrorSync` skips the repaint while the session is compacting (the local `compactionActive` plus the registry's `isCompacting`, which is the only signal for a window that never saw the start frame) — a mid-pass repaint drew a branch that was still being rewritten and cost seconds on a large session, which is the "GUI flashes and stutters while compacting" report; the header's ticking line is the feedback instead. The commit's item then rides the pass's **end frame** (`compactionEntry`, narrowed by `summarizeCompactionEntry` — facts, not the whole entry) and `handleCompactionEnd` draws it in place, id-keyed exactly like the history path's copy so the two can never double: a real pass adds one entry and leaves the rest of the branch alone (measured: 4851 entries in, 4852 out), so a reload is never what the item needs. Selecting a session whose process is compacting **waits** instead of loading it (the user-visible rule: show the wait, then load): the decision is made against a fresh `/api/instances` read — the poll is up to 5 s stale and a pass can start and end inside it — the status line is authoritative (not a transient that reverts), `waitForCompactionEnd` polls every 2 s with a 20-minute ceiling, and every new selection bumps `compactionSelectToken` so a superseded wait returns without touching the screen (verified live: 9 s of waiting, then the load ran as soon as the flag cleared). The flag has to survive all three registry hops — `applyInstancePatch`, `mergeInstanceEntry` **and `parseInstanceEntry`**, whose whitelist silently dropped it so `/api/instances` never showed a pass the writing process had published. The switch gate now allows 120 s (240 × 500 ms) rather than 5 s: `switch_session` is fire-and-forget over the broker, and a long session answered later than the old window allowed — the gate still returns the instant the matching snapshot lands, and a newer selection supersedes it. One trap worth knowing when editing this file: inside an `omp.on(...)` handler an undeclared `event` read resolves to the DOM global `event` (the extension project includes `lib.dom`), so it type-checks and lints clean and then throws at runtime in Bun — read the payload off the declared parameter.
- Tool status: `nextToolStatus` (`public/state.js`) orders a call's lifecycle (pending → streaming → complete/error, terminal is final) for both the state map and the pill, so a replayed start or a late update cannot walk a finished card back to "Working…" (which also restarted its pulse animation) and stale `statusLookup` renders always agree with the live state. The lookup is only as trustworthy as its last frame, so every path that can lose one settles the card: suppressed frames (a peek owns the surface, a deferred switch is pending) still fold into the state map and skip only the paint, `addHistoryResult` settles the pill from the session file for *both* outcomes (an error-only settle left "Working…" pulsing on a reloaded card forever), `finalizeToolCard`/`updateToolCard` re-target the element in `#messages` by `data-tool-call-id` when a repaint reset the renderer's index, `finishStreamingElement` flushes deferred cards even when the live element is already detached, and `agent_end` sweeps every call that is still open (its end frame was suppressed, dropped, or died with the process)

**3. Embedded server (`extensions/embedded-server.ts`)** — runs **inside** each omp process:
- HTTP: static assets, `/api/sessions`, `/api/search`, `/api/cost-dashboard`, `/api/files`, `/api/agent-settings`(+`PUT`/`reset`), `/api/agent-config`, `/api/models-config`, `/api/rpc`, `/api/instances`, `/api/lan-qr`, `/api/health`
- WS commands (shared dispatcher): prompt/steer/follow_up, abort/compact, get_state/set_model/set_thinking_level/cycle_thinking_level, list_commands, list_agents/get_agent_transcript, mcp.*, ui_response/ui_cancel, get_usage, run_omp_login, import_session, fork_session, list_memory_files, get_model_configuration/set_model_role/set_default_thinking_level/set_task_agent_*, auth key CRUD, session ops
- Forwarded events: message/tool lifecycle, auto-compaction, agents_changed, settings_changed, extension_ui_request (with replay), mirror_sync (snapshot re-broadcast on connect / session_start / session_switch — an in-place `switch_session` reloads no extension, so the `session_switch` re-broadcast is what lets the UI converge on the switched session)
- Session activity: each process mirrors its live session file + `isStreaming` flag into the shared `ompcot-instances` registry (rewritten on every forwarded event, plus a 3s audit that re-reads the entry and corrects a flag that outlived its run — a lost `agent_end` write or a `${pid}.json` inherited from a reused pid used to stay `true` forever) and `/api/instances` prunes dead pids. The entry is written through an in-memory copy with an atomic tmp+rename (a read-modify-write raced deletes and silently dropped later patches, and a torn read was indistinguishable from a dead pid — the file is now only unlinked on `ESRCH`, never on a parse failure), re-registration preserves the published run flag and `startedAt` (an extension reload mid-run used to blank it for a deduped whole interval), and a *sampled* `!ctx.isIdle()` only publishes `false` after three consecutive idle ticks (the value is momentary between messages and tool calls; `agent_start`/`agent_end` hints write immediately). Sidebar green dots are reconciled against that registry (`public/session-activity.js` on each instance poll) instead of trusting that a matching `agent_start`/`agent_end` pair arrived. The window's *own* process gets a split vote: its event stream leads on the *start* side — a stored `true` never re-adds a mark the local flag does not back (that flag is itself cleared by non-terminal events: `state.reset()` on a selection, a suppressed `agent_start`), and the foreground file survives a missing or clobbered entry — but a stored `false` wins outright and may *stop* the window's own run, because the registry only ever stores the debounced verdict (three consecutive samples, or a terminal end's explicit hint), never a momentary gap. The stored flag is `runtimeSettled(ctx.isIdle(), ctx.getAsyncJobSnapshot())` — `!isIdle()` plus the background-work half of the host's `hasPendingAsyncWork()` — i.e. the same `isRpcSessionSettled` predicate that backs the RPC mode's `session_settled`/`get_state.isSettled` and the TUI's own teardown: a `willContinue` pause *with* work in flight stays marked (its wake may still come), while a pause whose job finished or was cancelled (delivery suppressed by the host) is over for good. `public/app.js` settles on it when the window still says streaming and the foreground transcript has been frame-silent for `RUN_IDLE_SETTLE_MS` (8s, which also keeps a fresh run's first poll — before its `agent_start` hint lands — from being settled), logging `run.end {source:"runtime-idle"}`; without that path a non-terminal settle whose wake never comes held "Waiting…" and the streaming composer for good. Every `mirror_sync` bookkeeping path ORs the snapshot's momentary flag with the existing mark for the same reason
- Run lifecycle: `agent_end` is not always the end of a run. A `willContinue` end means the host already scheduled its own continuation (auto-retry, empty/unexpected-stop retry, compaction continuation) and its contract says subscribers must not treat it as a user-visible terminal settle; omp 18.3.3 added a second non-terminal case (`awaitingAsyncWork`, a background-work pause whose wake is not guaranteed) that never leaves the host. `agentEndContinues` (`public/state.js`) splits the two: a continuing end finishes the live message element and flushes its deferred tool cards, but the streaming state, the sidebar mark, the unread badge, the deferred `switch_session`, the resync-at-idle and the composer queue flush all wait for the terminal end — otherwise a paused run reads as idle and "resurrects" on the wake's `agent_start`. The registry write splits the same way (`runStateHintForEvent`, `extensions/embedded-server.ts`): an `agent_end` with `willContinue:true` publishes `isStreaming:true` (not `false`), so other windows' dots do not clear mid-run. The `awaitingAsyncWork` pause itself is still invisible to the extension — detecting it needs the upstream seam, and B15 (`ctx.getAsyncJobSnapshot()`) is the honest source for what a run is waiting on The GUI's own evidence for this is now explicit: `debugLog` records `run.end {willContinue, terminal, source}` at every end, the extension's broadcast summary carries `willContinue`/`awaitingAsyncWork`/`isTerminal` (a bundle without them could not explain a session that "never stopped"), and a continuing end sets the label to `status.waiting` ("Waiting…") instead of "Working…" — a pause is not progress, the dot keeps breathing as the activity light, and the abort button stays as the way out (the runtime's own settled verdict, not the non-terminal frame, is what finally lets go of the run — see the registry paragraph).
- Huge sessions: the transcript is not shipped or painted whole. A `mirror_sync` carries at most `SNAPSHOT_ENTRY_LIMIT` (400) entries — the live *tail* — plus `totalEntries`/`truncated`, because the full session as one WS frame measured 18.5 MB and each repaint blocked the main thread for ~6 s on a 4826-entry session (and a session *selection* did it twice: the history fetch, then the snapshot). The frontend pairs a truncated snapshot with what it already has: a snapshot for the session the DOM already shows is **kept** (live frames keep it current; replacing it would drop the conversation), and a snapshot for anything else — a window that never drew it, a peek just released — hydrates through `hydrateTranscriptFromRuntime` (`get_messages` in full, time-sliced). Every full paint goes through one of two renderers. A *search* keeps the forward, time-sliced `renderTranscriptFromEntriesChunked` (80 entries per slice, `setTimeout(0)` between slices — a match can be anywhere, so the whole transcript has to be in the DOM for the highlight to find it). Every other paint is **tail-first** (`public/transcript-hydration.js`): the newest slice is laid out first, the caller anchors the viewport to it, and earlier slices are pulled in when the reader comes within 240 px of the top — prepended *above* the loaded content with `scrollTop` compensated by exactly the inserted height, so the reading position never moves (`#messages` sets `overflow-anchor: none`, or the browser's own scroll anchoring compensates a second time). Measured on a 5622-entry session: the newest entries were on screen ~0.7 s after the click, viewport already at the bottom and the session's first entry *not* in the DOM; each scroll-up load adds ~50 items and `scrollTop` grew by exactly the inserted height (3313 = 6705−3392, 5175 = 11880−6705; 67 loads to reach the top, ~167 ms each — two layout flushes on a growing 3600-item DOM). The row above the oldest loaded entry (`transcript.loadEarlier` / `transcript.loadingEarlier`) is both the manual affordance and the loading indicator, and it disappears when the session's first entry lands; the hydration also keeps pulling slices while the viewport is not covered, because a tail of short entries would otherwise leave a half-empty, unscrollable screen with nothing to trigger the next load. `cancelHydration()` runs at the top of every `renderSessionHistory`: a resync or a snapshot repaint renders *without* a view token, so without it a stale hydration would prepend into the new view and leave its row behind. Both modes carry an abort check (`transcriptView.token` + `shouldContinue`) so a newer claim — another selection, a subagent peek — stops the rest of a render from landing on top of it; the chunked mode reports progress through `status.renderingTranscript`. Tail-first renders slices newest-first, which is why the session cost/context totals are folded out of the entries (`applyTranscriptTotals`) instead of accumulated by the render walk — the walk no longer sees most of the transcript, and the header must not show the cost of however far the reader has scrolled — and why a tool result drawn before its card (a slice boundary between a call and its result) is held in `ToolCardRenderer.pendingHistoryResults` until the card lands instead of being dropped (`createHistoryCard` drains it). The cost that remains on a long session is **whole-transcript relayout**: `#messages` is a flex column of content-sized children, so a content write anywhere invalidates the column's layout, and the next geometry operation (the follow's clamp, the hydration's compensation read) pays for all of it — measured 16.7–28.6 ms per content change at 80k nodes / 3775 items, which is what "the GUI stutters but the CPU sits low" is (one short blocking task per update, the process idle in between). Coalescing the follow caps it at one relayout per animation frame; the structural fix would be containment — an A/B gave `.message, .tool-card, .notice-block { content-visibility: auto; contain-intrinsic-size: auto 140px }` **0.07 ms** for the same measured frame (versus 27 ms), but off-screen items are then sized by estimate, which moves the scroll geometry by ~244k px until they are rendered and would break the exact anchoring the hydration relies on. Doing it safely needs the recorded height of every item (which the hydration could take for free from the layout it already forces), so it is deliberately left for its own change. A second super-linear cost sat one layer up, in the *streaming* preview: `renderStreamingMarkdown` ran the vendored `remend` repair over the whole partial message, and remend is quadratic in its input — measured on a partial answer built from `**bold** \`code\` [link](url)` lines: 10 KB 0.13 ms, 30 KB 92 ms, 50 KB 211 ms, 200 KB 2.9 s, against 6.9 ms for `renderMarkdown` on the same 200 KB — so one long answer froze a frame per delta. The repair now runs over the last two lines only (`streamRepairWindowStart`, capped at `STREAM_REPAIR_WINDOW` = 4 KB): that is the entire region where anything can still be *open*, because this renderer's inline patterns never span a line break, and the window carries the fence state in (a fence opened earlier still gets closed for the renderer, which only matches paired fences). Same input: 1.8 ms (50 KB) / 7.4 ms (200 KB), and any text shorter than the window takes the original path bit-for-bit. Tool output is not the same problem: omp caps a tool result at ~50 KB (measured across this workspace's sessions: 0.05 MB max, ~2000 results), and the card's update path measured 0.1 ms for a 1 MB write. `renderedTranscriptFile` is the DOM's own identity for these rules, set when a render starts so a partial paint is never mistaken for "nothing rendered here". `omp --export` writes next to its session by default, not into the workspace (`omp-session-<name>.html` was landing in the repo and no window could ever open it: the sidebar addressed `/api/sessions/<absolute path>` — one segment — against a two-segment route, and `/api/open` ran the macOS-only `open` command). The export result is parsed (`Exported to: ` stripped, relative answers resolved) and handed to the OS by the extension (`openPathWithOs`, `cmd /c start "" "<path>"` on Windows).
- Session notices: omp persists the notices its TUI shows as `custom_message` entries (`display:true`: `async-result` for a delivered background-job result, `launch-completion`, `lsp-late-diagnostic`; `display:false` ones like `mid-run-todo-nudge` stay hidden) and no extension event announces one. They are transcript items, so both paths render them: `renderTranscriptFromEntries` maps them through `MessageRenderer.renderNotice` for history/snapshot/resync, and the extension diffs the session entries on the quiet lifecycle frames (`newDisplayableNotices` / `forwardSessionNotices` / `NOTICE_CHECK_EVENTS`) to broadcast a `session_notice` frame for the live path. Both paths key on the session-entry id (`data-notice-id`), so a snapshot that drew a notice and the live frame for the same entry cannot show it twice; the block carries an i18n'd label plus the raw `customType` as a tag, unwraps a `<system-notice>` envelope, and clamps long job payloads like a thinking block. While a peek owns the transcript, `session_notice` is suppressed with the other transcript-drawing events (`public/transcript-view.js`)
- Manual compaction (`case "compact"` → `startGuiCompaction`): `AgentSession.compact` **rejects** on every failure path — a no-op (`ManualCompactionNoOpError`: "Already compacted", "Nothing to compact (session too small)"), a summarizer error, a pass already in flight — and omp treats an unhandled rejection as fatal: the process exits and every window on that port dies with it (18.4.0: a second Compact on an already-compacted session printed `[Unhandled Rejection] ManualCompactionNoOpError` and exited 1). `options.onError` fires only for failures raised inside compact's own try block ("Compaction already in progress" is thrown before it), so the returned promise's rejection is the only *complete* signal and is consumed here — that is what turns a failed compaction into a message instead of a dead workspace. Focus instructions must be the positional argument (`ctx.compact("…")`): a `customInstructions` key inside the options object is ignored by the host, and the two forms are mutually exclusive (the string form carries no callbacks, so its outcome comes from the promise). On commit the fresh snapshot goes out *before* the terminal frame, so the repaint's history-derived token count (the kept tail's last assistant usage — still the pre-compaction size) is superseded by the frame's live `contextUsage`
- Reduced motion: every animation in the stylesheets must survive the `prefers-reduced-motion: reduce` block actually *stopping* rather than strobe. Chromium/WebView2 map the Windows "Animation effects" setting to that media query, and the block shortens `animation-duration` to 0.01 ms — with `animation-iteration-count` left `infinite`, every infinite animation (the streaming status pill's pulse, the sidebar/Agent-Hub dots, the streaming caret) became a ~100 kHz flicker instead of no motion: the purple tool-status capsule blinked while the non-animated gray pending pill looked fine. The block caps the iteration count at 1 (the animation runs once, instantly, and rests at its base style); any new `infinite` animation is covered by that rule, so verify a pill/dot change under reduced motion before calling it done. One deliberate exception: `.status-indicator.streaming` keeps breathing (4.5 s, opacity 1 → 0.35) under reduced motion, because it is now the only signal that a run is still alive while the model thinks or runs tools (the transcript caret is gone for those phases) — an activity light that cannot move is not one, and 4.5 s cannot strobe; a second exception is the transcript's typing caret (`.message-content.streaming .streaming-text.typing::after`), which the same cap left *lit and frozen* — indistinguishable from a text cursor parked after text that stopped arriving, because the settled state draws no caret at all — so it blinks at 1.4 s under reduced motion too
- Provider/model freshness: omp's `ModelRegistry` + `AuthStorage` are boot-time snapshots, so `get_available_models` / `list_auth_status` run `resyncModelSources()` first — `credentials.poll()` (external-commit probe) plus a `models.yml`/`auth.json` mtime+size gate around `registry.refresh()`. Providers/models/keys added by another process (`omp login`, another window, a hand edit) appear without restarting the workspace; the composer dropdown re-fetches on open and the Providers page reloads on every activation (its models.yml editor keeps unsaved drafts)

Key data flow: user action → `window.tauriNative.*` or WS command → embedded-server → omp surfaces (ExtensionAPI / in-process settings+registry / CLI fallbacks).

## Post-fix verification (Rust / Tauri)

After every edit under `src-tauri/`, run `bun run check:rust` (cargo check + clippy -D warnings + fmt check) and only mark complete on exit 0. Never run `tauri build` for verification. NOTE: on Windows bash environments, coreutils `link` can shadow MSVC `link.exe` and break cargo check — run from a VS Developer Shell if that happens.
