> 2026-09-28 (B11 + B12 shipped, plus the streaming-pill flicker diagnosed):
>
> - **B11** — `runStateHintForEvent` (`extensions/embedded-server.ts`) + `agentEndContinues` (`public/state.js`) split "the turn ended" from "the run ended": a `willContinue` end finalizes the live message element and flushes its deferred cards, but the registry flag, the sidebar mark, the unread badge, the deferred `switch_session`, the resync-at-idle and the queue flush all wait for the terminal end. Unit-tested on both sides (`state.test.js`, `embedded-server-instance-registry.test.ts`); a real `willContinue` end was not reproducible on demand, so the live trigger is the one part not observed end-to-end. The 18.3.3 `awaitingAsyncWork` pause stays invisible to extensions either way — upstream seam.
> - **B12** — displayable `custom_message` notices now render on both paths: history/resync via `MessageRenderer.renderNotice` (`public/message-renderer.js`, `public/session-resync.js`) and live via a synthesized `session_notice` frame (`newDisplayableNotices`/`forwardSessionNotices` in the extension, `app.js` case), keyed on the session entry id so a snapshot and a live frame cannot double it. Live-verified on the probe workspace: a seeded `async-result` renders exactly once (hidden `mid-run-todo-nudge` skipped, envelope unwrapped), and a real background job produced a notice mid-session with no reload.
> - **Agent Hub `main` row (follow-up, not an omp gap)** — clicking "view transcript" on the main row could land the window on a different session even when the live session was on screen: omp registers the main agent once, at process start, and its registry ref keeps that registration's session file, so after a `new_session`/switch/fork the row named a session the process had left (reproduced live on the user's running process: roster main `...21-13-28...jsonl` vs the process session and `/api/instances` `...22-22-17...jsonl`). The click compared that stale path against the window's live files, missed, and peeked the stale session's transcript. Fixed at both ends: `applyLiveMainSession` (`extensions/embedded-server.ts`) rewrites the main row's `sessionFile` from the published ctx (the source `/api/instances` already uses), the hub passes the row's kind with the click, and `resolveTranscriptOpenAction` treats `main` as "return to the live view" — never a peek — while the remaining path comparison normalizes separators/`\\?\`/case. Verified live: the fixed roster's main row matches the process session, and clicking it issues no `get_agent_transcript` and leaves the transcript and active session untouched (extension command log + DOM).
> - **Streaming-pill flicker (not an omp gap, found while probing 18.3.x runs)** — with Windows "Animation effects" off (`SPI_GETCLIENTAREAANIMATION = 0` → `prefers-reduced-motion: reduce`), the app's reduced-motion block shortened every `animation-duration` to 0.01 ms but left `animation-iteration-count: infinite`, so each infinite animation ran as a ~100 kHz strobe: the purple `.tool-status.streaming` capsule blinked (measured 0.78/0.38 square wave on a 1.5 s pulse) while the non-animated gray pending pill looked fine. Fixed by capping the iteration count in `public/style.css`; the streaming pill now holds opacity 1.00 (98 samples over a run) and the dot/caret animations rest at their base style instead of strobing.

> Manual compaction's event surface (2026-09-28, v0.8.20; found while fixing "compaction has no feedback and freezes the page"): **`auto_compaction_start`/`auto_compaction_end` are automatic-path events.** In `pi-coding-agent@18.4.0` they are emitted by `runAutoCompaction` (reasons `threshold`/`overflow`/`idle`/`incomplete`, actions `context-full`/`remote`/`snapcompact`/`handoff`) and by the shake path — a *manual* pass emits neither, and that covers both `ctx.compact` (the GUI command) and the `/compact` builtin dispatched through the RPC prompt frame. The seams that do fire for every path are `session.compacting` (inside the summarize step; gated on `extensionRunner.hasHandlers("session.compacting")`, which is why registering a no-op handler is what makes the long part observable) and `session_compact` (`{compactionEntry, fromExtension}`, on commit). A shake rewrites the branch's entries without committing a compaction entry, so it emits `auto_compaction_end` with no `session_compact` after it. Consequence for the GUI: the whole manual lifecycle is assembled in `nextCompactionLifecycle` from those two seams plus the command's own promise. Separately, a command's own result text — `/compact` prints `Compaction complete. Tokens: 148880 -> 41441 (saved 107439).` — travels as an RPC `command_output` frame on the process's **stdout**, which the broker deliberately drops (`omp_manager.rs`: stdout is `Stdio::null()` on this path), so no window can see it; the GUI takes its numbers from `ctx.getContextUsage()` instead. `session.scan`-style commands that report only through `command_output` are unobservable to the GUI for the same reason.

> Runtime provider/model resync (post-v0.8.5): omp snapshots provider/model knowledge at process start — `models.yml` is parsed by `ModelRegistry`'s constructor and credentials are loaded into `AuthStorage` over the SQLite `agent.db` — so a provider, model, or key added while Ompcot ran (`omp login` / `omp config` in a terminal, another workspace window, a hand edit) stayed invisible to the model picker and the Providers page until the workspace restarted. `get_available_models` / `list_auth_status` now run `resyncModelSources()` first: `authStorage.credentials.poll()` (omp's external-commit probe) plus a `models.yml`/`auth.json` mtime+size gate around `ModelRegistry.refresh()`, so an unchanged list read costs a stat + two SQLite reads. The frontend matches that contract: the composer model dropdown re-fetches on every open, and the Providers page is a reload-on-open page (its models.yml editor skips the refetch while the textarea holds unsaved edits).

This document records which omp capabilities the GUI does **not** expose today, split by remediation cost, plus explicit non-gaps. Use it as the backlog source when planning GUI feature work.

> **Status review 2026-10-06 (omp 18.4.2 → 18.6.1, GitHub release bodies + live probes against `omp/18.6.1`): two real breaks found and fixed.** Every release body in the window (18.4.3–18.4.12, 18.5.0, 18.5.1, 18.6.0, 18.6.1; 18.4.7 is a bare version bump) triaged against this document's consumption surface, then verified on a scratch session driven through `omp --mode rpc` (both with and without `extensions/dist/embedded-server.mjs` loaded):
>
> - **The fork frame split (18.4.11) — the GUI's "fork from here" was destructive on every build since.** The RPC `fork` command was added ("fork into a new session file and switch to it: history up to and including `entryId`"), and `session_before_branch`/`session_branch` gained `reason` (`"branch"` drops the entry, `"fork"` keeps it, `"btw"` promotes a `/btw` answer) "so handlers can tell whether `entryId` is dropped (branch) or kept (fork)". Live-probed on 18.6.1: `{"type":"fork","entryId":"u1"}` leaves only `u1` in the new session file (old file untouched) and fires `session_branch {reason:"fork"}`; `{"type":"branch","entryId":"u1"}` returns `{text:"first user message"}` and leaves the new session **empty** — it is the esc-esc rewind, and the GUI's `fork_session_core` was sending it. "Fork from here" therefore cut at the wrong end (the forked-from message and its tail were dropped) and reported success. Fixed: `fork_session_core` sends `fork` on ≥18.4.11 and keeps `branch` only for older builds (`supports_rpc_fork`, version-gated off the cached `omp --version`; an unparseable version defaults to the non-destructive frame), and the `session_branch` waiter (`public/session-branch.js`) matches `reason:"fork"` so a `/btw` promotion or rewind can no longer confirm a pending fork (unlabelled pre-18.4.11 events still match).
> - **Command reports left the transcript (18.5.0) — `/context`, `/jobs`, `/mcp list`, … showed nothing.** " `/changelog`, `/context`, `/tools`, `/hotkeys`, `/advisor status`, `/memory view|queue|stats|diagnostics` … no longer add their report to the transcript", and the reports now ride `command_output` frames on RPC stdout (live-probed: `/context` answers `{"type":"command_output","text":"…"}` + a synchronous `response`, no `prompt_result`) — a lane `interesting_rpc_frame` dropped.
